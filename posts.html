18 May 2026 Performance Front-end

How this site adapts to low-RAM devices

The portfolio now classifies your device into one of three tiers and only enables expensive effects on tiers that can afford them. Here's how, and why it matters when your audience runs cheap Chromebooks.

I run this site on a few different machines: a desktop with a discrete GPU, an older laptop with integrated graphics, and a phone. The 3D phone showcase in the Projects section uses Three.js — it's heavy on the laptop and embarrassing on the phone. Same story for the cursor-follow aurora behind the hero, and the magnetic pull on the "Say Hello" button.

Hiding those on small screens is the easy half. The harder question is: what about the 13-inch laptop with 4 GB of RAM that might run them poorly? That's where most viewers of a UTS student portfolio actually sit.

The classifier

One function, run before any of the new effects mount, stamps a tier class on <body>:

function detectPerfTier() {
    const reduced  = matchMedia('(prefers-reduced-motion: reduce)').matches;
    const saveData = !!(navigator.connection && navigator.connection.saveData);
    const lowMem   = navigator.deviceMemory != null && navigator.deviceMemory <= 2;
    const lowCpu   = navigator.hardwareConcurrency != null
                  && navigator.hardwareConcurrency <= 4;

    if (reduced || saveData || lowMem || lowCpu) return 'low';

    const knownHighMem = navigator.deviceMemory >= 8;
    const knownHighCpu = navigator.hardwareConcurrency >= 8;
    const fineHover    = matchMedia('(hover: hover) and (pointer: fine)').matches;
    if (knownHighMem && knownHighCpu && fineHover) return 'high';

    return 'mid';
}

Three signals matter:

  • prefers-reduced-motion — user-controlled. Always respected.
  • Save-Data — set by some mobile plans and corporate proxies. If the browser tells me bandwidth is precious, I assume the device is too.
  • deviceMemory / hardwareConcurrency — Chrome and Edge expose these. Safari doesn't, so the function falls back to mid: never assume high without explicit evidence.

The trick is keeping the baseline feel good. Even on perf-low the page still has a moving scroll bar, a letter-by-letter hero reveal, and stats that count up — small touches that read as polish without costing frames.

What I avoided

  • CSS filter: blur() on large elements. Falls back to CPU on some integrated GPUs. The aurora uses radial gradients with transparent stops to fake the soft falloff for free.
  • Continuous mousemove handlers. Magnetic pull and card spotlight only listen while hovering the element itself, and coalesce with requestAnimationFrame.
  • Animating box-shadow, top, left. Only transform and opacity on hot paths — both composite on the GPU.

Most of these aren't novel; they're the standard "don't make the browser do layout/paint every frame" rules. What's worth doing is measuring on a real low-end device and assuming that person is the median viewer, not the exception.
